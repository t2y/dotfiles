# Go コーディング規約

全プロジェクト共通で使う Go の規約。
新規コードを書くとき、既存コードをリネームやリファクタするとき、レビューで指摘するときに従う。

## 命名

### 構造体名は単数形

複数のコンポーネントを束ねる集約構造体や DTO であっても、型名を複数形にしない。

```go
type Controller struct {  // Controllers ではない
    User  *UserController
    Group *GroupController
}
```

**Why:** Go の型名は単数形が慣習。集約であることは型名ではなくフィールドが表す。

### コンストラクタは戻り値で New / Make を使い分ける

- ポインタ（`*T`）を返す関数は `New`（`NewXxx`）
- 値（`T`）を返す関数は `Make`（`MakeXxx`）

```go
func NewNotification() *Notification { ... }
func MakeUser() User                 { ... }
```

**Why:** 呼び出し側が名前だけで戻り値がポインタか値かを判別できる。標準ライブラリの `new`（ポインタ）/ `make`（値・参照型）の直感とも整合する。

**How to apply:** 違反を見つけたら直す。値を返す `NewXxx` は `MakeXxx` へ、ポインタを返す `MakeXxx` は `NewXxx` へ。

### bool 述語は Is / Has / Can で始める

bool を返す述語メソッドは `Is` + 状態の形を優先する。

```go
func (a *Auth) IsTOTPDisabled() bool { ... }  // ○
func (a *Auth) TOTPBlocked() bool    { ... }  // × 名詞＋受動態後置
func (a *Auth) DisablesTOTP() bool   { ... }  // × 三単現は響きが好まれない
func (a *Auth) DisableTOTP() bool    { ... }  // × 動詞原形はミューテータに読める
```

**Why:** 述語は `Is*` / `Has*` / `Can*` が主流で、文として読める三単現よりも `Is` で始まる状態表現が好まれる。

**How to apply:** 語の選択は運用上のニュアンスに合わせる。「拒否している」なら `Blocked`、「その機能を使わないので無効にしている」なら `Disabled`。

### map は値の型で単数命名する

`map[K]V` のフィールド・変数名は、キーではなく値（V）の単数名にする。

```go
message map[string]string   // messages ではない
b.message[msgStarted]
```

**Why:** map は「キーを渡すと1つの値が返る」ので、返る値の名前で呼ぶ。

**How to apply:** キーは const にまとめてタイポを防ぐとよい。

## ファイル内の配置

### callee を caller より上に置く

呼び出される関数（callee）を、呼び出す関数（caller）より上に配置する。依存の葉（他を呼ばない小さなヘルパー）を上、それらを組み合わせる関数を下にする。

**Why:** ある関数を読むとき、その中で呼ぶ補助関数がすでに上で定義済みになり、上から下へ読み下せる。

**How to apply:** コンストラクタ（`NewXxx` / `newXxx`）は例外で、従来どおりメソッド定義の後（ファイル末尾）に置く。この2つが相反する場合はコンストラクタ末尾配置を優先する。

## エラー

### `%w` はメッセージの末尾に置く

```go
fmt.Errorf("tag %s: %w", tag, ErrJobNotFound)      // ○
fmt.Errorf("%w with tag: %s", ErrJobNotFound, tag) // ×
```

**Why:** Go 標準ライブラリの慣習は「コンテキスト: %w」の形式で、文頭 `%w` は標準パターンから外れる。

**How to apply:** sentinel エラーを wrap するときも含め、常に `fmt.Errorf("<context>: %w", err)` の形にする。

## コメント

### 意図と背景だけを簡潔に書く

コメントに書くのは「なぜそうしたか」であって「何をしているか」ではない。

```go
// 一時エラーは次の reconcile で回収されるので、ここでは握って先に進む。
if isTransient(err) {
    continue
}

// err が一時エラーなら continue する   ← × コードを読めばわかる
```

**Why:** 実装詳細を書いたコメントはコードと二重管理になり、コードを変えたときに必ず陳腐化して嘘になる。一方、なぜその実装を選んだかはコードに書けないので、コメントでしか残せない。

**How to apply:**

- 処理の逐次説明、引数やフィールドの再掲、自明な分岐の説明は書かない。
- 書く価値があるのは、コードから読み取れないものに限る。なぜこの方法を選んだか、なぜ素直な方法を採らなかったか、前提にしている外部の制約（プロトコルの仕様、ライブラリの癖、既知のバグ、運用上の事情）、破ると壊れる不変条件。
- 長さは必要な分に留める。1文か2文で足りることが多い。段落を連ねた解説を関数の頭に置かない。
- コメントがないと追えないほど込み入ったコードは、コメントを足す前に、コードの側を分割・改名で読めるようにできないか検討する。
- コードを変更したら、その周辺のコメントがまだ正しいかを確認する。実態と合わなくなったコメントは直すか消す。
- doc comment（公開識別子の直上）は Go の慣習どおり識別子名で始める。それも何をするかの再掲ではなく、呼び出し側が知る必要のある前提や制約を書く。
